# Platform evidence inventory

Audit scope: current local source, tests, shared contracts, evaluation repository, and frontend. No live provider, hosted Supabase project, or production database was contacted. Provider response shape claims below are source-verified against mocked fixtures and the provider's [OpenAPI specification](https://github.com/alfaarghya/alfa-leetcode-api/blob/main/swagger.yaml), but live endpoint success and account-specific availability remain unverified.

The current adapter requests profile, solved, and contest endpoints concurrently. Profile and solved are required; contest is supplementary and failures are tolerated. Each request has an eight-second timeout and there is no retry. Existing mocked tests cover separate response shapes, partial solved values, optional contest failure, malformed input, timeout, network error, and provider status handling. The API error does not expose upstream URLs or exception details.

## Common persistence and evaluation path

1. GitHub and LeetCode adapters validate provider responses and return restricted normalized snapshots. Route authorization requires an approved recruiter and checks candidate ownership before provider access; request-scoped Supabase clients and existing RLS remain in use.
2. GitHub successful refresh updates the saved GitHub row; LeetCode provider refresh appends a new row. Candidate-entered platform data is separately marked `candidate_provided`, and the latest-read API returns provider sync and candidate-provided LeetCode records separately. Provider failure occurs before writes; a failed persistence operation does not update/erase the previous GitHub snapshot or delete prior LeetCode rows.
3. Evaluation repository's rubric `makeEvidence` path accepts existing `normalized_evidence` only when it already has the rubric contract's `evidenceId` and `evidenceType`. Provider snapshots do not meet that scoreable contract and are not converted into zeros or scores.
4. The v3 evaluation result separately contains the latest snapshot per source/provenance in `platformEvidence`: evidence ID, candidate ID, source, evidence type, availability, observed timestamp, normalized provider values, verification status, provenance, `freshness: 'unassessed'`, limitations, and supporting/not-appropriate category mappings. The record remains distinct from rubric-scored `evidence`. Duplicate refresh snapshots are not all copied into the same evaluation context.
5. AI explanation receives deterministic scores and bounded platform context with explicit unverified limitations; AI references may cite platform evidence IDs. It cannot set or change scores. The UI displays source/provenance, retrieval time, availability, limitations, and contextual mappings. An unsuccessful refresh leaves existing saved evidence available.

## Scoring use and open evidence policy

Direct scoring still requires reviewer/assessment evidence with an explicitly configured evidence type, an explicit category mapping, and an already normalized value from 0 to 100. The current system has no agreed threshold mapping from repository metadata, solved counts, or contest statistics to that scale. Therefore GitHub/LeetCode contribute contextual observations to the evaluation and AI explanation where relevant, but do not satisfy score sufficiency and do not change a numeric category or overall score. This is deliberate fail-closed behavior, not a claim that the platform values are useless.

No maximum age or stale-data rule is configured. Snapshots therefore report freshness as `unassessed`; freshness should not be represented as verified/current. No production schema change is required by the additive JSON response context, but existing production migration-history/schema reconciliation remains unverified and blocks deployment independently.
