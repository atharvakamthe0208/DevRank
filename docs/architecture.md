# Architecture

DevRank is a modular monolith: `apps/web` calls `apps/api`, the API coordinates repositories and services, and `packages/contracts` owns shared Zod schemas and inferred TypeScript types. The API owns provider secrets and mediates database access. Platform adapters normalize evidence independently; unavailable integrations should not prevent evaluation of available evidence.

The API separates Express app setup (`src/app.ts`) from startup (`src/server.ts`). Routes are mounted under `/api`; middleware owns request validation, bearer-token verification, recruiter approval checks, 404 responses, and consistent errors. The web app uses Supabase Auth for recruiter sign-up, email confirmation, login, password recovery, session restoration, and logout. Signup creates a recruiter profile in `pending` status; protected recruiter pages and candidate API routes require a confirmed email and approved recruiter profile. Admin review routes additionally require an approved admin profile and database functions recheck that role before listing or deciding applications.

The candidate repository scopes queries by the verified user ID as well as relying on database RLS. Supabase uses the public/anonymous key with an authenticated user's verified JWT so Row Level Security remains active. No service-role key is used. Database migrations add restrictive approval and owner policies while preserving existing policies; they must be reviewed and applied to the intended Supabase project separately. The first admin must be provisioned by a trusted project owner through the SQL procedure in `authentication.md`.

The scoring module is deterministic and owns numeric scores under the active six-category v3 contract. The canonical categories and original preliminary six-category weights include Communication Skills, sourced from the Day 4 rubric. Five-category v2 and six-category v1 results remain read-only. The AI module may explain validated scores and unverified platform context, but its output cannot alter scores, weights, evidence, or status. Evaluation create/retrieve/history routes validate and persist results; configured-role and owner-defined-role flows remain distinct, and previous five-weight role profiles are not rewritten. GitHub and LeetCode snapshots are included in a separate typed platform-evidence context with provenance, observed time, limitations, and supporting mappings. They are not numeric scoring evidence until explicit normalization rules are approved. Owner-scoped dashboard, comparison, and ranking APIs validate stored results and scoring-version compatibility. Production availability remains dependent on the separately blocked migration audit and approved deployment plan.

The GitHub service uses the official REST API and is isolated from route handlers. Candidate-scoped GitHub sync and LeetCode sync/manual submissions pass shared validation and approved-recruiter plus owner checks before being saved to `platform_evidence`; GitHub and LeetCode sync store validated public snapshots with `github_api` and `alfa_leetcode_api` provenance respectively, while manual values use `candidate_provided` provenance. Evaluation reads the most recent snapshot per source/provenance and keeps it separate from rubric-scored evidence. Third-party provider output is not independent identity verification. No LeetCode credentials or session cookies are requested. See the [platform evidence inventory](quality/platform-evidence-inventory.md) for exact data paths and the [evaluation evidence mapping](quality/evaluation-evidence-mapping.md) for scoring boundaries.
