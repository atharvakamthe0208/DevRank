# Architecture

DevRank is a modular monolith: `apps/web` calls `apps/api`, the API coordinates repositories and services, and `packages/contracts` owns shared Zod schemas and inferred TypeScript types. The API owns provider secrets and mediates database access. Platform adapters normalize evidence independently; unavailable integrations should not prevent evaluation of available evidence.

The API separates Express app setup (`src/app.ts`) from startup (`src/server.ts`). Routes are mounted under `/api`; middleware owns request validation, bearer-token verification, recruiter approval checks, 404 responses, and consistent errors. The web app uses Supabase Auth for recruiter sign-up, email confirmation, login, password recovery, session restoration, and logout. Signup creates a recruiter profile in `pending` status; protected recruiter pages and candidate API routes require a confirmed email and approved recruiter profile. Admin review routes additionally require an approved admin profile and database functions recheck that role before listing or deciding applications.

The candidate repository scopes queries by the verified user ID as well as relying on database RLS. Supabase uses the public/anonymous key with an authenticated user's verified JWT so Row Level Security remains active. No service-role key is used. Database migrations add restrictive approval and owner policies while preserving existing policies; they must be reviewed and applied to the intended Supabase project separately. The first admin must be provisioned by a trusted project owner through the SQL procedure in `authentication.md`.

The scoring module is deterministic and owns official numeric scores and rankings. The AI module may explain validated evidence and scores, but its structured output cannot alter them. AI, data collection, normalization, and scoring remain separate responsibilities. Scoring, AI, and business APIs are not yet implemented.

The GitHub service uses the official REST API and is isolated from route handlers. Candidate LeetCode/HackerRank submissions pass shared validation and owner authorization before being appended to `platform_evidence`; provenance remains `candidate_provided`, and those values are not independently verified. No restricted platform scraping is used.
